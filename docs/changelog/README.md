## 2026-09-15 — Discovery: the five known limitations resolved

- **New capability — place services are searchable** (`20260915100000`): `place_service.search_tsv` + GIN index and a services branch in `_search_place_pool`, so "sauna" or "braids" finds places that offer it, ranked below name and category matches. Perf harness gained 100,000 services. (`architecture/discovery-search-and-recommendations.md` 1.0 → 1.1, `architecture/perf/discovery-2026-09.md` 1.0 → 1.1)
- **Behaviour change — mobile type-ahead goes through the API**: `GET /api/mobile/search/suggest` (180 a minute per user or IP, programme switches) replaces the direct anon `search_suggest` call, reversing the earlier hybrid decision at the owner's request. Both platforms now log suggestion requests (`surface = 'suggest'`) and the suggestion opened; `admin_search_insights` reports them separately (`20260915100100`) and Admin › Discovery gains three type-ahead tiles (`admin/discovery.md` 1.0 → 1.1, `admin/metrics.md` regenerated). App builds from before this change keep the direct call until they update.
- **New capability — Expo push receipts** (`20260915100200`): accepted tickets are kept in `push_receipt`; the minute delivery job reads receipts about 15 minutes later, deletes tokens reported `DeviceNotRegistered` and logs every other provider error. (`operations/notifications-and-email-operations.md` 1.0 → 1.1, `operations/scheduled-jobs.md`, privacy inventory and retention)
- **New capability — web push**: browsers can turn on notifications in Settings › Notifications (`web_push_subscription`, `push-sw.js`, `webPushCore` with the `web-push` package); every notice that pushes to the app reaches them. Endpoints are limited to real push services; sign-out and account deletion remove subscriptions. Inactive until `WEB_PUSH_VAPID_PUBLIC_KEY`, `WEB_PUSH_VAPID_PRIVATE_KEY` and `WEB_PUSH_SUBJECT` are set on the web deployment. (`security/secrets-and-environment.md`, `apps/web/.env.example`)
- **New capability, switched off — recommendation email** (`20260915100300`): the same digest by email for people who opt in, a consent record (`notification_consent_event`), signed and one-click unsubscribe, send-time checks, an admin switch that requires confirming legal item G1 and `RECOMMENDATION_EMAIL_KILL_SWITCH`. Must stay off until G1 is Decided. (`LEGAL_REVIEW_REQUIRED.md` G1/G3 updated)
- **Fix — the web push service worker was behind sign-in**: the first production check found `/push-sw.js` answered `307` to `/auth/signin` for anyone signed out, because `proxy.ts` matched it like a page. Browsers refuse a redirected worker script and re-check it signed out, so registration and updates would have broken. It is now excluded from the proxy and served `Cache-Control: no-cache`.

## 2026-09-15 — EAS environment: the disabled anon key that broke every release build

- **Fix — the mobile app's Supabase key had been disabled for eleven days.** `EXPO_PUBLIC_SUPABASE_ANON_KEY` in all three EAS environments (development, preview **and production**) was still the legacy anon key, and Supabase disabled legacy API keys on this project on 2026-09-04. Every direct-to-PostgREST read the app makes came back `401 {"message":"Legacy API keys are disabled"}`, so event detail, place detail, reviews, highlights and claims failed in any EAS build while working perfectly in the dev client — the local `.env` holds the rotated key, and Metro inlines whichever key is present at build time. Diagnosis needed the elimination in order: the previous preview build failed the same way (not the maps fix), a 13-September build predating R8 failed the same way (not minification), every server query returned 200 (not the API), and the dev client worked (release-only). Comparing the local and EAS key hashes found it. All three environments were updated with `eas env:update` and re-checked: each now returns 200. **Rule: rotating a Supabase key means updating `eas env` too — the repo's `.env` files do not reach a cloud build.**
- **Fix — `EXPO_PUBLIC_CLOUDINARY_CLOUD_NAME` was missing from EAS entirely.** Impact was narrower than it first looked and was checked rather than assumed: uploads were never at risk, because the server's signature response carries `cloudName` and the upload path uses that. Only the highlight thumbnail and trim URLs built client-side in `useHighlights.ts` were broken. Added to all three environments.
- **Note — `EXPO_PUBLIC_API_BASE_URL` differs between local and EAS, and EAS is the correct one** (`https://abontenhub.com`). The local `.env` points at a Vercel preview deployment. No change made.
- **Fix — the map picker's header sat underneath the status bar** (`apps/mobile/src/components/explore/MapPickerSheet.tsx`): a `Modal` fills the whole window under edge-to-edge, so its header has to clear the status bar itself. "Choose on map" overlapped the clock. It now applies `insets.top`, matching `ImageCropModal`. A sweep of the other seven `Modal` screens found they all already handled it.
- **Verification — maps confirmed drawing on a release build.** Google tiles, labels, POIs and markers render on all four map surfaces of the preview APK on a device: the location picker (Accra, then Kumasi after a geocoded search), the explore/social map, event detail and place detail. Both surfaces that were previously unverifiable are now verified end to end, with no crash and no JavaScript error in logcat.

## 2026-09-15 — Android launch readiness, round 2: ban enforcement, claims, discovery and bookings

- **Behaviour change — Account restrictions** (`20260915020000`): a suspended, banned or deleted account can no longer write anything other people see. `getMobileAuth` already refused them on every `/api/mobile` route, but mobile deliberately writes a large part of the app straight to PostgREST under RLS, and none of those policies looked at `status_id` — nor did `send_message`, which is `EXECUTE`-able by `authenticated`. Confirmed against production: a banned account still holding its pre-ban JWT posted a `place_review` that landed `approved` and public. A `BEFORE INSERT OR UPDATE` trigger (`guard_restricted_account`) now covers reviews and their photos, highlights, stories, places and their photos/services/opening hours, events and their occurrences/media/ticket types/promo codes, messages and reactions, bookings, place claims and their documents, reports and attachments, `user_info`, and the two payout-destination tables. Writes with no `auth.uid()` — service_role, `pg_cron`, migrations — are never blocked. Private-to-the-user rows (drafts, favourites, device tokens, notification read-state) are deliberately not guarded.
- **Behaviour change — Place claims** (`20260915030000`): `approve_place_claim` decided who was an admin from the `p_admin_id` argument the caller passed, and `EXECUTE` was granted to PUBLIC — while its sibling `approve_place_claim_and_verify` was already service_role-only. A non-admin passing a real admin's id (readable by anyone through `user_info_public_select`) got past the check and was stopped only by RLS on the row lock. `EXECUTE` is now service_role-only, and when `auth.uid()` is not null it must equal `p_admin_id`. The admin console is unaffected: it calls with a service-role client and a pre-resolved `AdminContext`.
- **Behaviour change — Organizer earnings** (`20260915010000`): `record_organizer_earning` fills `organizer_ledger_entry.transaction_id` by resolving the payment from the tickets it has just issued, so an earning joins to the charge that paid it in one step. All 28 existing rows were backfilled. Amounts, the conflict key and the fee split are unchanged.
- **Behaviour change — Bookings**: a booking request nobody answered before its date arrived now reads as **expired** on all four surfaces and can no longer be accepted or declined (`respondToPlaceBookingCore` returns 409). Nothing ever moved a `place_booking` out of `pending`, so a request for a date already gone still showed a live "Cancel booking" to the customer and live Accept/Decline to the owner — and accepting it told the customer their past date was confirmed. The state is derived (`@abonten/core/placeBooking`), not stored: no new status value, no sweep job, and an unanswered request stays unanswered in the record.
- **Fix — "See all similar events" returned nothing**: the page de-slugged the category in the URL by hand, but `generateSlug` strips `&` and commas, so `"Music & Concerts"` came back as `"Music Concerts"` and `get_similar_events` (which filters on `lower(event_category)`) matched no rows. 18 of the 19 top-level categories were affected. Slugs now resolve against the canonical category list (`@abonten/core/eventCategoryLabels`), with `undoSlug` still the fallback for search terms and locations.
- **Fix — duplicate saved cards and wallets**: the card de-duplication used PostgREST `contains`, which is exact JSON containment, so Paystack's inconsistent brand casing and trailing whitespace defeated it; mobile money had no de-duplication at all. Matching now happens against a normalised key, and the brand is trimmed on the way in. The one duplicate pair in production was retired.
- **Fix — mobile review titles**: both mobile review hooks call the shared `formatTitle` instead of their own copy of the destructive per-word transform, so a title typed in the app is stored the same way the web stores it.
- **Correction — offline writes**: the report, review and place-claim sheets read the mutation's own `isPaused` and say "Waiting for connection…" with a line explaining it, instead of sitting on "Submitting…" indefinitely. The queued write is still delivered intact on reconnect; only the wording changed.

## 2026-09-14 — Android launch-readiness audit: money-path, authorisation and keyboard fixes

- **Behaviour change — Ticket checkout** (`20260914203000`): a basket may hold more than one ticket type again. `ticket_checkout_one_pending_per_user_event` (a unique index on `(user_id, event_id) WHERE status = 'pending'`) could not tell the second LINE of one order from a second ORDER, because `create_ticket_checkout` writes one row per ticket type — so any Regular + VIP basket aborted with "You already have a pending ticket checkout for this event" when no such checkout existed. The rule now lives in the function behind a transaction-scoped advisory lock on `(user, event)` and is checked before the reservation loop; the replacement index `ticket_checkout_one_pending_line_per_type` keeps one pending row per ticket type.
- **Behaviour change — Refunds**: `cancelUserTicketCore` refuses a ticket whose status is `used`. The attendee list hid "Cancel" once a ticket was checked in, but `POST /api/mobile/tickets/cancel` and the web action accepted it, released the seat and queued the Paystack refund — so someone already scanned in at the door could get their money back by calling the endpoint. The compare-and-set also excludes `used`, and the zero-rows branch re-reads instead of reporting a cancellation that did not happen.
- **Behaviour change — Event reviews** (`20260914213000`): eligibility is enforced by a `BEFORE INSERT` trigger mirroring `postEventReview.ts` (not the organizer, not cancelled, event ended, reviewer holds a `used` ticket). RLS only checked `auth.uid() = reviewer_id`, and mobile writes reviews straight to PostgREST, so any signed-in account could review any event — stored `approved` and, because the column defaulted to `true`, badged as a verified attendee. `is_verified_attendee` is now set by the trigger and defaults to `false`. `place_review` stays deliberately ungated.
- **Behaviour change — Check-in**: `checkInTicketCore` takes the event whose gate is scanning and 404s a ticket belonging to a different event of the same organizer, which the existing copy ("That code doesn't match a ticket for this event") had already promised. `POST /api/mobile/organizer/tickets/:id/check-in` accepts an optional `eventId`.
- **Behaviour change — Android keyboard**: the chat composer and the shared `KeyboardAwareScrollView` avoid the keyboard with `behavior="padding"` on Android. Both had assumed `windowSoftInputMode=adjustResize` resizes the window, which an edge-to-edge app (`edgeToEdgeEnabled=true`) is not; measured on Android 15, the composer sat behind the keyboard and submit buttons were unreachable across the auth screens and the event wizard.
- **Behaviour change — Session expiry**: a 401 from `/api/mobile/**` now drops the dead session. The typed client returns HTTP error statuses in the body rather than throwing, so React Query's expiry handler never saw them and the app sat signed-in-looking with every screen failing. Only the token a request actually used may condemn the session, so a stale in-flight 401 cannot revoke a newly created one.
- **Correction — event dates**: `validateSpecificDates` applies the start-before-end rule `validateSingleDateRange` already had (an inverted occurrence used to reach the `occurrence_time_check` constraint as "Something went wrong!"), and the native wizard shows the error on the schedule step instead of at Publish.
- **Correction — report sheet**: the validation and server errors render in the sticky footer beside the button, not below the fold where they were invisible.
